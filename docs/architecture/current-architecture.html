Current Architecture Review

A2A Platform Go 当前架构设计说明

基于当前代码重新梳理，而不是复用旧文档结论。本文覆盖服务端、内置 Agent 引擎、外部 Agent 代理、群组编排、人类客户端、观测与数据模型。

代码基线：当前工作区 主服务：Go + net/http 存储：MySQL 8 前端：React + Vite
一句话定位

A2A Platform 是一个带持久化、权限边界、任务追踪和群组协作能力的 Agent 中枢：它注册 Agent，代理 A2A 消息与 AgentCard 发现，运行内置 LLM Agent，并把人类、外部 Agent、桥接 Agent 放进同一个 group 协作边界中。

总览 模块 流程 群组编排 Human Client 数据模型 API 运行部署 当前边界

1. 系统总览

A2A Platform 当前由一个 Go 服务承载主要后端能力：HTTP API、A2A 代理入口、内置 Agent 引擎、Bridge Agent 调用、SSE 事件流、嵌入式 Admin SPA。MySQL 是唯一持久层，保存 Agent、Task、Message、Trace、Context、Subagent、Group、Invite、Artifact 等状态。

协作边界

Group 是成员发现、权限校验、群聊事件、自动产物和编排状态的边界。人类和 Agent 都必须作为成员进入 group。

3. 关键流程

3.1 服务启动流程

启动时服务先建立 MySQL 连接并迁移 schema，然后恢复 Agent 连接状态，注册配置里的 builtin/bridge Agent，启动 Registry 后台健康检查，最后挂载 API 和 Admin SPA。收到 SIGINT/SIGTERM 后，服务会先用 10 秒超时关闭 HTTP server，再通过 ServiceContext.Close() 停止健康检查并关闭 MySQL；主流程会等待这些清理完成后再记录服务已停止并退出。

3.2.1 平台托管 AgentCard

平台返回给调用方的公开 AgentCard 会重写为平台代理面：url 和 supportedInterfaces[0].url 都指向 /agent/{name}，protocolBinding 为 JSONRPC，protocolVersion 为 1.0，并默认声明 capabilities.streaming=true、defaultInputModes=["text/plain"]、defaultOutputModes=["text/plain"]。

3.3 A2A 消息代理流程

/agent/{name} 是统一代理入口。它会注入或调整 contextId，创建本地 task，保存用户消息和 send trace，然后根据目标 Agent 类型走三条路径：内置 Engine、Bridge Agent、外部 HTTP Agent。代理 trace 和内置 Engine 的 tool_call trace 在持久化前会通过共享脱敏模块处理已知敏感字段、Bearer token、Admin token、agent secret、human/member token、API key、URL 凭据和敏感 query 参数；外部代理的普通响应体或 SSE 字节流仍按协议透传给调用方。内置 Engine 执行工具和子代理时使用原始 arguments/result/task/context，但发给前端的工具/子代理展示事件、保存到消息历史的工具 arguments/result，以及保存到 subagent session 的 task/context/messages/result/error 会写入脱敏副本。

/agent/{name} 代理分发

flowchart TD
  Req["POST /agent/{name}<br/>JSON-RPC / A2A"] --> Parse["解析 body<br/>提取 message/contextId"]
  Parse --> Context["按 context_mode 注入/清空 contextId<br/>解析 root/parent headers"]
  Context --> Task["创建 task: PENDING<br/>保存 user message<br/>写 send trace"]
  Task --> Type{"目标类型"}
  Type -->|Builtin| Builtin["Engine.HandleRequest<br/>LLM + tools<br/>SSE"]
  Type -->|Bridge| Bridge["BridgeAgent.HandleRequest<br/>HTTP/CLI skill<br/>SSE"]
  Type -->|External| External["HTTP POST 到 conn.Url<br/>透传 JSON 或 SSE"]
  Builtin --> Done["保存 agent/tool message<br/>task=RESPONDED/ERROR<br/>写 response/stream trace"]
  Bridge --> Done
  External --> Done
  Done --> Client["响应调用方"]

外部 HTTP Agent 连接失败时，代理会把本地 task 置为 ERROR，并写入经过 URL/凭据脱敏的 error trace，避免把带 token 的上游地址或传输错误细节原样落库。恶意或异常上游行为也有 e2e 覆盖：HTTP 200 但返回 invalid JSON 不应导致平台 panic，破损 SSE 流关闭后不应让平台挂起。

3.4 内置 Agent LLM + Tool Loop

内置 Agent 先加载同一 context 的历史消息，再调用 provider 的流式 Chat API。模型若产出 tool calls，引擎会执行工具、记录工具消息，再把结果放回上下文继续下一轮。

  participant Engine as engine.Engine

  participant Tools as Platform Tools
  participant DB as MySQL Stores

4. Group 协作与编排

Group 是当前架构中最重要的新边界：它同时承担成员可见性、群聊事件、成员 token、自动产物、Agent-to-Agent 授权和编排状态描述。Admin 可以创建 group、维护成员和邀请；Human Client 用 invite token 加入；Agent 的平台工具也会被 group_id 限制。

当前实现状态： p2p 用于成员发现和直接 Agent 调用，不接受 group event 广播；leader_led 会触发 leader Agent；free_chat 会让候选 Agent 自主决定是否回复。roundtable、stateflow、research_long_horizon 当前主要体现在 orchestration state 的策略描述中，事件执行逻辑尚未完整展开。

5. Human Client 设计审查

apps/human-client 当前是一个“人类参与者房间 UI”，不是完整 A2A Agent。它不托管 AgentCard，不暴露 /agent/{name}，也不默认让人“扮演 agent”。它注册时只声明唯一 handle 和展示名，由平台分发 human token；默认加入 default-p2p，并拿到 group-scoped member token。

当前实现： Human 身份已从本地自报 client_id 升级为服务端身份。注册时 handle 全局唯一，重复返回 409；human token 由后端生成并返回给用户保存，前端不能修改。以后重新进入时可以用唯一 handle 登录，也可以用已保存的 token 登录。注册、name 登录和 token 登录都会为默认 default-p2p group 分发新的 group member token；使用 invite token 加入其他 group 时，后端会用 human token 里的 human_id 覆盖请求中的 actor_id，避免前端伪造身份。Human Client 登录后会周期性调用 /api/humans/me，平台据此更新 human_users.last_seen_at，Admin 的 Humans 页面用该字段判断在线状态。Admin 也可以修改 human 的 handle/display name 或删除 human，但不会读取或改写 token 明文。

当前设计的合理部分

  • human_users 保存不可变 human_id、唯一 handle、展示名和 last_seen_at；human_sessions 保存平台分发 human token 的 hash 和撤销状态。
  • 权限粒度是 group-scoped，而不是全局 human token；这和 group 作为协作/发现边界的设计一致。
  • 默认 group 行为和 simple-mode Agent 对齐：未指定 group 的 human 注册后进入 default-p2p。
  • Human Client 不进入全局 Agent Registry，也不被当作可调用 A2A Agent；这避免了把人类聊天 UI 误暴露成机器可调用服务。
  • Room 读取 group、members、events、artifacts、orchestration；在 default-p2p 中从 Participants 选择 agent 后，Human Client 用 group member token 直接调用 /agent/{name} 做点对点 A2A 消息。

仍需注意的边界

项目当前行为后续方向
human token注册时由平台生成，用户可保存；登录可以使用唯一 handle 或粘贴 token，不输入 password；Admin 不能反查旧 token 明文，但可以签发新 token 并一次性展示。可以增加 token 轮换、撤销和一次性展示策略。
多 session/token注册生成 human token；每次 name/token 登录和入群会新增 group member token；Admin 统计未撤销且未过期的 active sessions。可以增加登出、设备管理、旧 token 自动撤销或短 TTL。
token 存 localStoragehuman session 和 group access token 都存浏览器 localStorage。生产环境可改为 httpOnly cookie + CSRF 防护，或更严格的前端安全策略。
旧 invite join 兼容无 human session 的 /api/group-joins 仍保留旧的 actor_id 模式。后续可为 human actor 强制要求 human session，只给 agent/legacy client 留迁移窗口。

身份模型

概念含义校验规则
human_id服务端生成的不可变唯一用户 ID。由注册生成，不允许用户任意声明。
handle用户可输入的唯一登录/展示名，例如 alice。注册时全局唯一；重复注册拒绝；重新进入时可直接用 handle，也可用 human token。
display_name房间内展示名，可改名。可按 group 策略决定是否唯一，不作为认证依据。
human_session_token平台分发的人类身份 token。服务端只保存 hash；用户保存明文 token，用它重新进入。
group_member_token某个 human 在某个 group 的访问凭证。由 invite/join 颁发，绑定 human_id 和 group，支持撤销/过期。

是否要“人扮演 Agent”

如果目标只是让人参与讨论，保持 actor_type=human 是合理的。如果目标是让外部 A2A Client 把这个人当成完整 Agent 调用，则应另建一个“Human-backed Agent”能力：它需要注册到 Agent Registry、提供 AgentCard、拥有自己的 /agent/{name} 或平台代理入口，并把 A2A 任务转成人类待处理队列。这个能力不应和普通 Human Client 的 group room 身份混用。

6. 数据模型

当前 schema 由 internal/svc/servicecontext.go 内置迁移。核心设计是：Agent 连接状态、Human 身份与登录态、每次 A2A 调用的 task/message/trace、聊天 context、subagent/task item，以及 group 协作对象都在 MySQL 中持久化。

启动迁移分为两类：核心 CREATE TABLE IF NOT EXISTS schema 失败会使 NewServiceContext 关闭数据库连接并返回错误，阻止服务以不完整 schema 启动；兼容旧版本的 ALTER TABLE、索引补建、方向字段回填和 lineage 修复仍按 best-effort 执行，失败时记录调试日志但不阻断启动。

7. API 与权限面

Admin Token 面

  • /api/agents：Agent 注册、查询、更新、删除。
  • /api/agents/{name}/credential：Admin 查看 agent 注册 secret。该值当前在 agents.secret 中明文保存，因此可以显示；空 secret 会返回 unavailable。
  • /api/humans：Human 列表与在线状态，只返回身份、last seen 和 active session 计数，不返回 token。
  • /api/humans/{id}：Admin 查询、修改或删除 human；修改仅覆盖 handle/display name，删除会清理 sessions、group membership 和 group-scoped tokens。
  • POST /api/humans/{id}/tokens：Admin 为 human 签发新 session token；旧 token 只保存 hash，不能被反查。
  • /api/builtin-agents：内置 Agent CRUD，并同步 Engine 和 Registry。
  • /api/tasks、/api/traces、/api/contexts、/api/subagents、/api/stats：观测、统计和会话管理。
  • POST /api/groups、成员管理、invite 管理、group join 管理。

Human Session 面

  • /api/humans/register：创建唯一 handle 和 display name，返回后端分发的 human token，并自动加入 default-p2p。
  • /api/humans/login：用唯一 handle 或 human token 登录，返回 human 身份、新 human token 和新的默认 group member token。
  • /api/humans/me：用 Bearer human token 查询当前 human，同时刷新 last_seen_at，作为 Human Client 的轻量心跳。
  • /api/group-joins：如果带 human token，后端用 token 的 human_id 作为 human member actor_id。

Member Token 面

  • GET /api/groups：仅返回当前成员可见的 group。
  • /api/groups/{id}/members/events/artifacts/orchestration：限定在 token 所属 group。
  • DELETE /api/groups/{id}/members/{actorType}/{actorId}：Admin 可删除任意成员；member token 只能删除同 group 中与 token 绑定的自身 actor，删除时同步撤销该 actor 的 group member token。
  • /.well-known/agent-card/{name}、/agent/{name}/.well-known/agent-card.json 与 /agent/{name}：目标 Agent 必须是同 group 成员。
  • /api/group-joins：公开入口，用 invite token 换 member access token；invite 消耗、member upsert、response 所需成员列表读取和 group member token 创建在同一个数据库事务中完成，consume 按 status、过期时间和 max uses 做条件更新，避免超过可用次数或在 token 创建后因额外 DB 读取失败而丢失明文 token。

/health 始终返回 JSON；MySQL Ping 成功时返回 HTTP 200 与 status=ok，失败时返回 HTTP 503 与 status=degraded、db=error，同时继续报告 Registry 中已连接和总 Agent 数。

CORS 仍支持 cors_origins 白名单，但管理面请求有额外放行规则：实际请求如果携带合法 X-Admin-Token 或 Authorization: Bearer admin-token，服务端会回显该请求的 Origin；预检请求如果声明会携带 Admin header，也允许通过，真正权限仍由后续 authMiddleware 校验 Admin token。

8. 前端与运行部署

Admin UI 可以有三种运行形态：嵌入式构建通过 Go build tag frontend 把 web/dist 挂到主服务根路径；无头构建不注册 / SPA fallback，只暴露 API、A2A 代理和健康检查；compose 部署默认使用无头平台加独立 Admin 容器。当前 docker-compose.yml 使用 WITH_FRONTEND=0 启动无头平台，并用 web/admin/Dockerfile 构建 Nginx Admin 容器，Admin 容器把 /api、/health、/agent/ 和 /.well-known 反向代理到 platform:18090。Admin SPA 入口由 AdminAuthGate 保护：用户必须输入 Admin token，前端用 GET /api/agents 验证后把 token 存入 localStorage；失败 3 次后纯前端锁定 1 分钟，所有真实权限仍由后端 authMiddleware 校验。当前 Admin 左侧有 Agents 与 Humans 两个独立列表：Agents 看机器 Agent 连接状态，并可点进 Agent 详情查看 AgentCard、上游 URL、context mode 和注册 token；Humans 看人类参与者在线状态，并可点进 Human 详情修改 handle/display name、删除身份或签发新的 human token。Admin 本地开发态默认把 /api、/health、/agent/、/.well-known 代理到平台 http://127.0.0.1:18090；注意代理路径使用 /agent/ 而不是 /agent，避免误拦截 SPA 路由 /agents。本地开发可用 VITE_DEV_ADMIN_TOKEN 在 dev 模式下给受保护 API 自动附加 Admin token；生产构建不使用该兜底。Human Client 是独立 Vite 应用，开发态默认把 /api 代理到平台 http://127.0.0.1:18090；也可以通过 HUMAN_CLIENT_BFF 显式改走自己的轻量 server 转发。

9. 当前边界与设计判断

编排模式边界

Group mode 的状态描述比执行逻辑更完整。当前可认为 leader_led 和 free_chat 是主要可执行模式，其他模式是面向后续扩展的语义接口。

上下文边界

Agent 可声明 context 或 stateless。代理入口会根据 Registry 中的 context mode 决定是否保留 contextId。

安全边界

Admin token 管理全局资源；member token 只能访问所属 group，并且调用 Agent 或读取其代理 AgentCard 时要求目标 Agent 是同 group 成员；成员删除边界由 authMiddleware 注入的 trusted principal 判定，member 只能删除自己。

观测边界

Task/message/trace 是所有调用的主审计链路；代理、内置工具调用和子代理会话持久化前会脱敏已知 token/API key/secret 字段、URL 凭据和敏感 query 参数。内置工具/子代理执行仍使用原始值，UI 事件、消息历史和 subagent session 写入脱敏副本；外部代理响应和 SSE 字节按协议透传。

工具边界

工具注册是全局的。内置 Agent 获取基础工具、A2A 平台工具和动态工具；只读工具会并行预执行，写工具串行执行。

Bridge 边界

Bridge Agent 是进程内适配器，不是外部常驻连接。它按 skill 选择 HTTP/CLI target，并包装成 A2A SSE。
