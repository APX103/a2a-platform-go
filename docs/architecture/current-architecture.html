Current Architecture Review

A2A Platform Go 当前架构设计说明

基于当前代码重新梳理，而不是复用旧文档结论。本文覆盖服务端、内置 Agent 引擎、外部 Agent 代理、群组编排、人类客户端、观测与数据模型。

代码基线：当前工作区 主服务：Go + net/http 存储：MySQL 8 前端：React + Vite
一句话定位

A2A Platform 是一个带持久化、权限边界、任务追踪和群组协作能力的 Agent 中枢：它注册 Agent，代理 A2A 消息，运行内置 LLM Agent，并把人类、外部 Agent、桥接 Agent 放进同一个 group 协作边界中。

总览 模块 流程 群组编排 数据模型 API 运行部署 当前边界

1. 系统总览

A2A Platform 当前由一个 Go 服务承载主要后端能力：HTTP API、A2A 代理入口、内置 Agent 引擎、Bridge Agent 调用、SSE 事件流、嵌入式 Admin SPA。MySQL 是唯一持久层，保存 Agent、Task、Message、Trace、Context、Subagent、Group、Invite、Artifact 等状态。

  Human["Human Client<br/>apps/human-client"] -->|Group Member Token| API

  Tools --> API
核心中枢

/agent/{name} 是 A2A 消息代理入口，统一记录 task/message/trace，再按目标类型分发给内置、桥接或外部 Agent。

协作边界

Group 是成员发现、权限校验、群聊事件、自动产物和编排状态的边界。人类和 Agent 都必须作为成员进入 group。

内置智能体

Builtin Agent 由配置或数据库注册，支持 OpenAI/Anthropic provider、SSE 流式输出、工具调用、subagent 和任务工具。

3. 关键流程

3.1 服务启动流程

启动时服务先建立 MySQL 连接并迁移 schema，然后恢复 Agent 连接状态，注册配置里的 builtin/bridge Agent，最后挂载 API 和 Admin SPA。

启动流程

  participant Config as config.Load
  participant SC as svc.NewServiceContext
  participant DB as MySQL
  participant Reg as AgentRegistry
  participant Eng as Engine
  participant HTTP as net/http Server
  Main->>Config: 读取 etc/config.yaml 并展开环境变量
  Config-->>Main: Config
  Main->>SC: 初始化 ServiceContext

  end
  Main->>HTTP: 注册路由 + middleware + SPA
  HTTP-->>Main: ListenAndServe

3.2 Agent 注册与 AgentCard

外部 Agent 通过 POST /api/agents 注册。若请求提供 agent_card，平台托管静态 card；否则平台会访问上游 URL 发现 AgentCard 并做健康检查。

外部 Agent 注册

flowchart TD
  A["POST /api/agents"] --> B{"name 已存在?"}
  B -->|secret 匹配| C["允许幂等重注册"]
  B -->|不存在| D["继续"]
  B -->|冲突| X["返回 400"]
  C --> E{"请求提供 agent_card?"}
  D --> E
  E -->|是| F["规范化并标记 x_static"]
  E -->|否| G["fetch /.well-known/agent-card<br/>ping agent url"]
  F --> H["写入内存 connections"]
  G --> H
  H --> I["Upsert agents 表<br/>status=connected"]
  I --> J{"simple_mode?"}
  J -->|是| K["确保 default-p2p group<br/>加入 group_members"]
  J -->|否| L["返回注册结果"]
  K --> L

3.3 A2A 消息代理流程

/agent/{name} 是统一代理入口。它会注入或调整 contextId，创建本地 task，保存用户消息和 send trace，然后根据目标 Agent 类型走三条路径：内置 Engine、Bridge Agent、外部 HTTP Agent。

/agent/{name} 代理分发

flowchart TD
  Req["POST /agent/{name}<br/>JSON-RPC / A2A"] --> Parse["解析 body<br/>提取 message/contextId"]
  Parse --> Context["按 context_mode 注入/清空 contextId<br/>解析 root/parent headers"]
  Context --> Task["创建 task: PENDING<br/>保存 user message<br/>写 send trace"]
  Task --> Type{"目标类型"}
  Type -->|Builtin| Builtin["Engine.HandleRequest<br/>LLM + tools<br/>SSE"]
  Type -->|Bridge| Bridge["BridgeAgent.HandleRequest<br/>HTTP/CLI skill<br/>SSE"]
  Type -->|External| External["HTTP POST 到 conn.Url<br/>透传 JSON 或 SSE"]
  Builtin --> Done["保存 agent/tool message<br/>task=RESPONDED/ERROR<br/>写 response/stream trace"]
  Bridge --> Done
  External --> Done
  Done --> Client["响应调用方"]

3.4 内置 Agent LLM + Tool Loop

内置 Agent 先加载同一 context 的历史消息，再调用 provider 的流式 Chat API。模型若产出 tool calls，引擎会执行工具、记录工具消息，再把结果放回上下文继续下一轮。

Builtin Agent 执行循环

sequenceDiagram
  participant Client as Caller
  participant Proxy as AgentProxyHandler
  participant Engine as engine.Engine
  participant LLM as OpenAI/Anthropic Provider
  participant Tools as Platform Tools
  participant DB as MySQL Stores
  Client->>Proxy: SendStreamingMessage
  Proxy->>DB: task/message/trace
  Proxy->>Engine: HandleRequest(...)
  Engine->>DB: LoadHistory(contextId)
  Engine->>Client: SSE task.status working
  loop until no tool call or limits reached
    Engine->>LLM: ChatStream(messages + tool defs)
    LLM-->>Engine: text / reasoning / tool_call events
    Engine->>Client: SSE text.delta / thinking.delta
    alt tool calls exist
      Engine->>Client: SSE tool.call_start
      Engine->>Tools: Execute tool with source/root/parent/group context
      Tools-->>Engine: result or error text
      Engine->>DB: persist assistant/tool messages + trace
      Engine->>Client: SSE tool.result
    else final answer
      Engine->>DB: persist agent message
    end
  end
  Engine->>Client: SSE task.status completed

3.5 Subagent 与任务工具

ConfigureAuxiliaryAgentTools 会注册 spawn_agent 和 task system tools。spawn_agent 创建 subagent_sessions，以隔离上下文运行最多 3 个并发子代理，最长 5 分钟。

spawn_agent 子代理流程

flowchart LR
  Parent["父 Agent tool_call<br/>spawn_agent"] --> Create["创建 subagent_sessions<br/>status=running"]
  Create --> Run["SubagentEngine.RunExisting"]
  Run --> Limit{"activeCount < 3?"}
  Limit -->|否| Fail["标记 failed"]
  Limit -->|是| Loop["子代理 LLM loop<br/>仅使用基础工具"]
  Loop --> Complete["写 messages/result<br/>status=completed"]
  Complete --> Return["结果返回父 Agent<br/>作为 tool message"]
  Fail --> Return

4. Group 协作与编排

Group 是当前架构中最重要的新边界：它同时承担成员可见性、群聊事件、成员 token、自动产物、Agent-to-Agent 授权和编排状态描述。Admin 可以创建 group、维护成员和邀请；Human Client 用 invite token 加入；Agent 的平台工具也会被 group_id 限制。

当前实现状态： p2p 用于成员发现和直接 Agent 调用，不接受 group event 广播；leader_led 会触发 leader Agent；free_chat 会让候选 Agent 自主决定是否回复。roundtable、stateflow、research_long_horizon 当前主要体现在 orchestration state 的策略描述中，事件执行逻辑尚未完整展开。

4.2 群组消息与自动回复

POST /api/groups/{id}/events 写入群组事件。若请求 Accept: text/event-stream，平台会把原始事件、Agent delta、artifact 更新和 done/error 作为 SSE 帧返回。

Group Event 编排流程

flowchart TD
  E["POST /api/groups/{id}/events<br/>message"] --> Save["Append group_events"]
  Save --> Mode{"orchestration_mode"}
  Mode -->|p2p| Reject["409<br/>use direct agent chat"]
  Mode -->|leader_led| Leader["selectGroupLeader<br/>role=leader 优先"]
  Mode -->|free_chat| Candidates["freeChatCandidates<br/>排除 observer 和发送者"]
  Mode -->|其他模式| Reserved["返回当前 orchestration state<br/>执行逻辑未展开"]
  Leader --> Invoke1["内部调用 /agent/{leader}<br/>group contextId=group:{id}"]
  Candidates --> InvokeN["逐个调用候选 Agent<br/>最多 max_speakers"]
  Invoke1 --> Persist["Append agent group_event"]
  InvokeN --> Reply{"Agent 回复有效?"}
  Reply -->|NO_REPLY/空| Skip["跳过"]
  Reply -->|有效| Persist
  Persist --> Artifact{"auto_artifact enabled?"}
  Artifact -->|是| Upsert["Upsert group_artifacts<br/>leader-summary.md / group-discussion.md"]
  Artifact -->|否| Done["返回 triggered + orchestration"]
  Upsert --> Done
  Skip --> Done

5. 数据模型

当前 schema 由 internal/svc/servicecontext.go 内置迁移。核心设计是：Agent 连接状态、每次 A2A 调用的 task/message/trace、聊天 context、subagent/task item，以及 group 协作对象都在 MySQL 中持久化。

核心 ER 图

erDiagram

  tasks ||--o{ messages : task_id
  tasks ||--o{ traces : task_id
  contexts ||--o{ messages : context_id
  contexts ||--o{ tasks : context_id
  contexts ||--o{ subagent_sessions : parent_context_id
  contexts ||--o{ task_items : context_id
  a2a_groups ||--o{ group_members : has
  a2a_groups ||--o{ group_invites : issues
  a2a_groups ||--o{ group_member_tokens : grants
  a2a_groups ||--o{ group_events : records
  a2a_groups ||--o{ group_artifacts : produces

  agents {
    string name
    string type
    string url
    string status
    text agent_card_json
  }
  tasks {
    string local_task_id
    string source_agent
    string target_agent
    string context_id
    string root_context_id
    string state
  }
  messages {
    string task_id
    string role
    string sender_agent
    string recipient_agent
    text content
    json tool_calls
  }
  traces {
    string task_id
    string event_type
    string agent_name

    string orchestration_mode
    text rules_json
    text memory_policy_json

表用途关键关系
agents保存外部、内置、桥接 Agent 元数据、状态、AgentCard。tasks.target_agent 指向 Agent 名称。
tasks每次 A2A 调用的本地任务记录，包含 source/target/root/parent 链路。与 messages、traces 通过 local_task_id 关联。
messages保存 user/agent/tool 消息、reasoning、tool calls、发送方和接收方。按 context_id 支撑多轮历史。
traces记录 send/stream/response/tool_call/error 等观测事件。支持按 task、context、root context 查询。
contextsAdmin Chat 的会话容器。与 messages/tasks/subagents/task_items 形成工作上下文。
subagent_sessionsspawn_agent 的隔离执行记录。由父 context 和 tool_call_id 追溯。
a2a_groups协作空间，定义编排模式、规则、记忆策略和状态。拥有 members、events、artifacts、tokens、invites。
group_events群聊消息和编排错误等事件流。驱动 leader/free_chat 自动回复。
group_artifacts群组产物，支持人工创建和自动 upsert。自动产物按 group/name 更新 version。

6. API 与权限面

Admin Token 面

  • /api/agents：Agent 注册、查询、更新、删除。
  • /api/builtin-agents：内置 Agent CRUD，并同步 Engine 和 Registry。
  • /api/tasks、/api/traces、/api/contexts、/api/subagents：观测和会话管理。
  • POST /api/groups、成员管理、invite 管理、group join 管理。

Member Token 面

  • GET /api/groups：仅返回当前成员可见的 group。
  • /api/groups/{id}/members/events/artifacts/orchestration：限定在 token 所属 group。
  • /.well-known/agent-card/{name} 与 /agent/{name}：目标 Agent 必须是同 group 成员。
  • /api/group-joins：公开入口，用 invite token 换 member access token。

8. 当前边界与设计判断

编排模式边界

Group mode 的状态描述比执行逻辑更完整。当前可认为 leader_led 和 free_chat 是主要可执行模式，其他模式是面向后续扩展的语义接口。

上下文边界

Agent 可声明 context 或 stateless。代理入口会根据 Registry 中的 context mode 决定是否保留 contextId。

安全边界

Admin token 管理全局资源；member token 只能访问所属 group，并且调用 Agent 时要求目标 Agent 是同 group 成员。

观测边界

Task/message/trace 是所有调用的主审计链路；Group event/artifact 是协作房间的主审计链路，两者通过 group context 与 parent headers 间接连通。

工具边界

工具注册是全局的。内置 Agent 获取基础工具、A2A 平台工具和动态工具；只读工具会并行预执行，写工具串行执行。

Bridge 边界

Bridge Agent 是进程内适配器，不是外部常驻连接。它按 skill 选择 HTTP/CLI target，并包装成 A2A SSE。
