Chapter 09 · MVP Roadmap

MVP 路线：先把对象和验证做扎实，再追求自动科学发现

元研究系统非常容易膨胀。本章把第一版压缩到 8-12 周可以交付、可以验证、可以让真实研究问题跑通的范围。

MVP 的唯一目标

一个真实研究问题能在系统里完成完整对象链，并且 6 个月后回看时，每个 claim 仍然能追溯到 evidence、reasoning、review 和当时的验证状态。

第一版不要追求“AI 自动发现重大科学突破”。先做到：未验证 claim 不能入库，入库 claim 可追溯，研究分支可暂停恢复。

必须做与暂缓做

必须做 暂缓做 原因
7 类核心对象 CRUD 完整跨机构知识图谱 对象工作台是地基，跨机构复用可以后置。
V0-V2 + falsification V3-i/V4/V5 自动升级 高等级验证必须依赖真实复现和人类 gate。
PI 审批门 复杂委员会工作流 先证明人类 gate 的核心价值。
Root Context Composer 全功能研究模板市场 先让管理员能正确发起研究。
Branch Board 简化版 复杂可视化知识地图 先表达并行假设和阻塞状态。
Trace Log 完整审计合规系统 先保证每个对象有事件来源。

8-12 周路线

阶段 时间 目标 可验收产物
Phase 1 第 1-2 周 对象模型和基础 API。 Program、Question、Hypothesis、Evidence、Reasoning、Claim、Review 可创建和链接。
Phase 2 第 3-4 周 Root Context 和 UI 工作台。 管理员能发起研究；branch board 可见；claim inspector 可用。
Phase 3 第 5-6 周 V0-V2 验证和 review。 未 review 的 claim 不能入库；falsification 条件必填。
Phase 4 第 7-8 周 PI gate 和 durable wait。 审批请求、暂停、恢复、拒绝和修订都有事件。
Phase 5 第 9-10 周 agent 分工与对象写入。 Evidence Scout、Critic、Staff Officer 可按权限创建草稿对象。
Phase 6 第 11-12 周 真实研究 dogfood 和报告投影。 一条完整研究链路跑通，导出结构化报告。

MVP 成功标准

  • 从一个管理员输入的问题开始，系统生成 Program、Question 和至少一个 Branch。
  • 至少一个 branch 产生 Evidence、Reasoning、Claim 和 Review。
  • Claim 从 V0 升到 V2 的每一步都有硬门槛和事件记录。
  • Critic 的 objection 能创建 CounterEvidence 或 required changes。
  • PI 可以批准或拒绝 claim 入库，决定会写入 trace。
  • 导出的报告能从对象网络生成，而不是只拼接聊天记录。

第一版数据库范围

表/集合 用途 备注
research_programs 长期研究容器。 绑定 group/context/PI。
research_objects 统一存 Question/Hypothesis/Evidence/Reasoning/Claim/Review。 MVP 可用 JSON 字段加 type 区分。
research_edges 对象关系。 supports、contradicts、warrants、derivedFrom。
research_branches 分支状态。 保存 current_state、loop_guard、blockers。
research_events 审计和回放。 所有状态变化、审批、agent 写入都进事件表。
approval_requests PI gate。 支持 pending/approved/rejected/revision。

风险与取舍

复杂度过高

应对：第一版不做 V3+，不做复杂知识地图，只做对象链和 V0-V2。

用户不愿迁移

应对：支持从普通聊天或文档抽取对象，不强迫用户一次性结构化所有内容。

LLM 写入污染知识库

应对：agent 默认 draft_only；入库必须过 review 和 PI gate。

验证体系太学术

应对：UI 用简单状态呈现，底层保留严谨字段。
