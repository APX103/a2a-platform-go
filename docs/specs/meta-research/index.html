Meta Research System · Chapter Set

元研究分章规格：把深度研究写成可评审、可实现、可验证的系统

这一组 HTML 不是替代原来的总览页，而是把其中每个关键判断拆成可单独评审的章节。目标是让“深度研究”从一个好听的概念，落到对象模型、验证协议、编排状态机、治理门禁、UI 工作台和 MVP 路线。

分章目录

总览索引 00. 评审采纳矩阵 01. 定位与原则 02. 认识论与验证 03. 本体与溯源 04. 编排与状态机 05. 角色与治理 06. 新颖性与入库 07. 工作台 UI 08. 数据与协议 09. MVP 路线 10. 示例研究

为什么要拆分

单页总览适合建立共同语言，但不适合做严肃设计评审。元研究系统的难点不在于“列出很多 agent”或“生成一份研究报告”，而在于每个 claim 是否可追溯，每个状态是否能暂停恢复，每个验证等级是否有退出准则，每个新知识是否能区分组织内新颖与全局新颖。

本次拆分采纳了 Opus 评审中最关键的一组意见：单 FSM 不够、V3 复现定义不足、confidence 不能单值化、Reasoning 必须对象化、Critic 需要结构隔离、PI/Adjudicator 必须拥有明确权限、新颖性要分 scope。

章节地图

00 评审采纳矩阵 逐条判断 Opus 的建议：哪些采纳、哪些改写、哪些推迟到后续版本，并说明理由。 01 定位与原则 定义“深度研究操作系统”与普通 Deep Research 报告工具的边界，明确哪些事系统必须做，哪些事不做。 02 认识论与验证 展开 V 阶梯、证伪条件、证据设计等级、多维置信度、复现与独立复现的差异。 03 本体与溯源 把 Question、Hypothesis、Evidence、Reasoning、Claim、Review、Activity、Agent 建成一阶对象。 04 编排与状态机 从单 FSM 升级为 Program / Branch / Activity 三层编排，加入并行、暂停、恢复和 loop guard。 05 角色与治理 把 AI Research Lead 改为 Staff Officer，加入 PI、Adjudicator、Red Team Critic、Statistician 和 Curator。 06 新颖性与入库 区分组织新颖性、全局新颖性、理论新颖性、颠覆性、严谨性和意义，定义 Claim Ledger 入库规则。 07 工作台 UI 把研究界面从聊天窗口改成对象工作台：root context、branch board、claim inspector、approval queue。 08 数据与协议 给出关键 schema、事件流、状态转移 payload、审批门和外部工具集成协议。 09 MVP 路线 把系统约束到 8-12 周能交付的对象工作台、V0-V2、PI 审批、trace log 和基础报告。 10 示例研究 用“设计 A2A 深度研究编排系统”走完整对象链：问题、假设、证据、验证、claim、迭代。

整体架构一眼图

层 回答的问题 核心对象 必须可验证的输出
Research Program 长期研究为什么存在，边界是什么，谁有决策权？ Program, Scope, PI Gate, Knowledge Ledger 研究章程、阶段目标、审批记录
Hypothesis Branch 某个假设当前处在什么认知状态？ Question, Hypothesis, VerificationPlan, Claim 退出条件、反例条件、下一步动作
Activity / Tool 一次具体检索、分析、实验或审查如何执行？ Activity, ToolRun, Evidence, Artifact 输入、输出、参数、日志、可复现材料
Knowledge Ledger 什么能成为知识，什么只能保留为想法？ Claim, Reasoning, Review, CounterEvidence V 等级、confidence vector、novelty scope

当前结论

Opus 的评审里最在理的部分，是它把“看似完整的宏观设计”推进到了“长期运行时会不会坏”的层面。原总览页的方向是对的，但粒度不足。拆分后的版本把争议点显式化：系统不声称 LLM 能自动判定科学真理，而是定义一个让证据、推理、裁决和人类责任可见的操作系统。

所以本系统的核心口号需要收紧为：不是更好的研究报告，而是更持久、更可审计的知识生产过程。
