Chapter 07 · Workspace UI

工作台 UI：从聊天窗口转向对象、分支和验证状态

深度研究的前端不应该默认是一块聊天记录。聊天可以发起问题和解释状态，但研究主体应该是 root context、branch board、对象 inspector、claim ledger、approval queue 和 trace。

核心 UI 判断

用户进入一个研究系统时，最重要的问题不是“我能不能和群聊天”，而是“我正在研究什么、当前有哪些假设分支、哪些证据支持它、哪些 claim 卡在验证或审批上”。因此主界面必须围绕研究对象，而不是围绕消息流。

但“不做群聊”不等于“不能输入问题”。管理员需要明确入口来发起 root context：输入研究问题、选择入口 agent 或 flow、生成 Program/Branch，并把第一条问题写入 trace。

首页布局

区域 展示内容 主要动作
Program Header 研究目标、范围、PI、状态、风险、最近更新。 编辑范围、暂停、归档、导出报告。
Start Topic / Root Context 问题输入、入口 agent、使用模板、引用资料。 创建 root context、创建 branch、自动发送第一步。
Branch Board 每个假设分支的状态、阻塞、confidence delta。 打开分支、暂停、合并、升级审批。
Object Stream 最近创建的 Evidence、Reasoning、Claim、Review。 筛选、审查、转入 ledger。
Approval Queue 等待 PI / Adjudicator / Curator 的 gate。 批准、拒绝、要求修订。

不同群模式对应不同 UI

这是平台产品形态的关键规则。群的 orchestration mode 决定 UI，不应该所有群都渲染成同一个聊天窗口。

群模式 UI 主体 输入入口 不应该出现
P2P Network 成员发现、直连入口、能力卡片、Start Topic。 管理员从 Start Topic 发起 root context，或打开某个 agent 的 direct chat。 群广播聊天框。
Manual Flow 步骤编排器、每步 agent、system prompt、输入输出 artifact。 Start Topic 输入研究问题，选择入口 step 或 agent。 所有成员无序群聊。
Stateflow 状态图、当前 phase、可发言角色、gate 和 trace。 根据 state 选择允许的 action，而不是自由聊天。 绕过状态机的普通输入框。
Free Chat 聊天时间线 + 对象抽取侧栏。 聊天输入框。 把所有消息默认当知识。
Research Program 对象工作台、branch board、ledger、approval queue。 Root Context Composer。 单一线性聊天作为主界面。

Root Context Composer

这是管理员发起研究的入口。它不是普通聊天框，而是一个结构化启动器。

Question

用户输入自然语言问题。系统会生成 Question 对象，并保留原文。

Scope

选择研究范围、排除项、时间边界、数据源权限。

Entry Agent / Flow

选择第一步由哪个 agent、哪个 step 或哪个模板接管。

Mode

探索、验证、复现、综述、实验设计、知识复审。

Initial Materials

附加文档、链接、数据库、已有 claim、上下文片段。

Governance

选择 PI、审批策略、风险等级和自动化上限。

Branch Workspace

打开一个 hypothesis branch 后，页面应围绕状态推进，而不是围绕聊天。

组件 目的 用户动作
State Ribbon 显示当前 branch 状态、退出条件、阻塞项。 查看下一步、请求升级、暂停。
Hypothesis Card 展示假设、预测、反例条件。 修订假设、拆分分支。
Evidence Table 展示证据来源、设计等级、支持/反驳方向、独立性。 添加证据、标记同源、请求检索。
Reasoning Graph 可视化 Evidence → Warrant → Claim。 审查推理、定位漏洞。
Activity Log 显示工具执行、实验、审批和状态转移。 复现、查看输入输出、回滚草稿。

Claim Inspector

Claim 是系统最重要的 UI 对象。Inspector 必须让用户一眼看见这个 claim 处在什么知识状态。

  • Statement：声明内容和适用 scope。
  • Verification：V 等级、EvidenceDesignLevel、复现状态。
  • Confidence：truth、replicability、generalization、update log。
  • Reasoning：warrant 列表、推理类型、已知弱点。
  • Counter Evidence：反例、替代解释、未解决 objection。
  • Governance：reviewer、PI gate、下一次复审触发条件。

关键交互规则

所有自然语言输入都应该产生或修改对象，而不是只追加消息。比如用户问“这个结论靠谱吗”，系统应该打开 Claim Inspector，生成 Review task，而不是只在聊天里回答“看起来靠谱”。
  • Start Topic 生成 root context，并创建 Question。
  • “提出假设”生成 Hypothesis，而不是普通 assistant message。
  • “找证据”生成 Activity 和 Evidence。
  • “为什么成立”生成或打开 Reasoning。
  • “这个能入库吗”触发 Ledger Admission Review。
  • “我不同意”生成 Objection 或 CounterEvidence。
