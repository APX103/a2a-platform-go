1项目概述

1.1 目标

构建一套生产级别的纯 A2A（Agent-to-Agent）代理平台。平台作为 Agent 间通信的中间层，提供注册、发现、保活和消息转发能力。Agent 通过自研 Bridge 对接平台 API 或 MCP 服务来接入。

核心定位
平台是一个透明的消息代理——不参与 Agent 内部逻辑，只负责"谁在线"和"消息怎么到"。所有 A2A 协议消息都经过平台转发，但不解析消息内容的语义。

1.2 第一版范围 V1 必做

Agent 注册与发现

Agent 通过 REST API 注册到平台，提交 AgentCard（名称、地址、能力描述），平台维护可用 Agent 列表。考虑使用 etcd 的 lease + watch 机制实现。

保活机制

支持长连接（SSE）和定时 poll 两种保活模式，Agent 可按场景选择。SSE 断开或 poll 超时均触发下线。

消息代理

所有 Agent 间消息通过平台转发，遵循 A2A 协议（JSON-RPC SendStreamingMessage），平台只做协议层面的路由和转发。

API 接口 + MCP 服务

REST API 提供 Agent 管理、消息发送接口；MCP 端点暴露 list_agents、send_to_agent、get_agent_info 等工具和资源。

1.3 明确不在第一版范围

  • Bridge 的具体实现（Agent 自行对接平台 API 或 MCP）
  • 内建 Agent（LLM Agent 引擎）
  • 会话管理、多轮对话上下文
  • 消息追踪（Trace）与可观测性
  • 前端管理界面

2.2 Agent 注册与发现

注册流程

  1. 提交注册：Agent 启动后调用 POST /api/agents，提交名称、地址（URL）、AgentCard
  2. 写入 etcd：平台将注册信息写入 etcd，创建带 TTL 的 lease（默认 30s）
  3. 抓取 AgentCard：平台访问 AgentURL/.well-known/agent.json 获取 AgentCard（能力、版本、健康端点）
  4. 存入数据库：持久化 Agent 信息（名称、URL、AgentCard JSON、状态）
  5. 通知上线：通过 etcd Watch 和 SSE 事件广播通知其他组件

AgentCard 数据结构

/.well-known/agent.json 响应格式
namestringAgent 唯一名称，用于路由寻址
descriptionstringAgent 功能描述
versionstringAgent 版本号
urlstringAgent 服务地址
skillsarray能力列表，每个 skill 含 id、name、description、tags、examples
health_urlstring可选，下游健康检查端点（用于检测 Bridge 背后的 LLM 是否可用）

发现机制

  • REST API：GET /api/agents 返回所有在线 Agent 列表及其 AgentCard
  • MCP 工具：list_agents 以自然语言形式返回 Agent 列表
  • MCP 资源：a2a://agents 返回 JSON 格式的 Agent 列表
  • etcd Watch：内部组件可监听 Agent 上下线事件，用于实时状态同步

为什么用 etcd 而非纯数据库

etcd 方案
  • lease + keepalive 天然适合"注册 + 保活"，比自建心跳更可靠
  • Watch 机制实时感知 Agent 上下线，无需轮询
  • 支持集群部署，多平台实例共享状态
  • 分布式锁可用于 Leader 选举（全局调度）
纯数据库方案（当前原型使用）
  • 无额外基础设施依赖
  • 自建心跳：每 30s 检查一次，连续 3 次失败标记下线
  • 自建发现：查询数据库，无实时通知能力
  • 重启后从数据库恢复连接（当前原型的 RestoreConnections）
  • 不支持多实例水平扩展

2.3 保活机制

两种模式并存，Agent 可按场景选择：

长连接模式（SSE）

适合需要实时接收事件的场景

  • Agent 与平台建立 SSE 长连接 GET /api/events
  • 连接断开即触发下线逻辑
  • 平台通过 SSE 推送事件（Agent 上下线、任务状态变更）
  • 内置 30s keepalive 心跳包防止连接超时
定时 poll 模式

适合无法保持长连接的场景（Serverless 等）

  • Agent 定期调用 POST /api/agents/{name}/heartbeat 续约
  • 续约间隔由 Agent 决定，平台设定超时阈值
  • etcd lease TTL 自动过期处理下线
  • 建议续约间隔 ≤ TTL/3（如 TTL 30s，续约间隔 10s）

健康检查三态模型（当前原型实现）

当前原型已实现一个三态健康检查模型，生产版本可在此基础上改进：

状态含义触发条件
connectedAgent 在线可用注册成功 / 心跳正常 / 重连恢复
unreachableBridge 可达但下游不可用AgentCard 端点可达，但 health_url 返回非 200
offlineAgent 完全不可达连续 3 次心跳失败，AgentCard 端点不可达

自动重连机制

平台定期扫描数据库中状态为 offline/disconnected 的 Agent，尝试重新抓取 AgentCard。如果成功则自动恢复为 connected 状态并更新内存连接表，无需人工干预。

2.4 消息代理

协议

A2A JSON-RPC over HTTP/SSE，遵循 Google A2A 规范。

消息格式

{
  "jsonrpc": "2.0",
  "id": "request-1",
  "method": "SendStreamingMessage",
  "params": {
    "contextId": "optional-session-id",
    "message": {
      "role": "ROLE_USER",
      "parts": [{"text": "你好"}]
    }
  }
}

完整转发流程

  1. 接收请求：发送方 Agent 调用 POST /agent/{target_name}，平台读取请求体
  2. 解析协议：解析 JSON-RPC 结构，提取消息文本、contextId 等字段
  3. 创建 Task：为每条消息创建 Task 记录（UUID），状态 PENDING
  4. 查找目标：根据 {target_name} 在内存注册表中查找目标 Agent 地址
  5. 记录发送 Trace：记录 source agent、target agent、请求内容、时间戳
  6. 转发请求：向目标 Agent 发起 HTTP POST，设置 Accept: text/event-stream、A2A-Version: 1.0
  7. 代理 SSE 流：目标 Agent 的 SSE 响应逐 chunk 转发给发送方
  8. 记录响应 Trace：解析 SSE 中的文本内容，记录最终响应
  9. 更新 Task 状态：PENDING → WORKING → RESPONDED（或 ERROR）

Task 状态机

PENDING → WORKING → RESPONDED ERROR (转发失败)

SSE 事件类型

事件方向说明
task.status平台 → 客户端任务状态变更（working/completed/failed）
text.delta平台 → 客户端增量文本内容
thinking.delta平台 → 客户端推理/思维过程增量
tool.call_start平台 → 客户端工具调用开始（含参数）
tool.call_end平台 → 客户端工具调用结束
tool.result平台 → 客户端工具执行结果

设计原则

  • 只做转发：平台不解析消息内容的语义，不理解"这是一段代码"或"这是一个问题"
  • 记录元数据：记录每条消息的来源、目标、时间戳、状态，用于问题排查
  • 不管理会话：contextId 由 Agent 侧维护，平台只透传。会话状态、上下文历史由 Agent 自行处理
  • 超时保护：转发请求设置 180s 超时（当前原型的设定），避免无限等待
  • 透明代理：对 SSE 和非 SSE 响应均支持透传，保留目标 Agent 的原始 Content-Type

2.6 MCP 服务详细设计

连接流程

  1. 建立 SSE 连接：客户端连接 GET /mcp/sse，平台返回 endpoint 事件（含 session_id）
  2. 发送初始化：客户端通过 POST /mcp/messages?session_id=xxx 发送 initialize 请求
  3. 协商能力：平台返回协议版本 2024-11-05、支持的能力（tools + resources）
  4. 正常交互：客户端调用 tools/list、tools/call、resources/list、resources/read

暴露的工具

工具参数返回说明
list_agents—Agent 名称、描述、状态列表列出所有已注册 Agent
send_to_agentagent_name、messageAgent 响应文本向 Agent 发消息并等待回复（内部调用 POST /agent/{name}）
get_agent_infoagent_nameAgent 详情 JSON获取 Agent 详情（类型、状态、技能列表）

暴露的资源

URI类型说明
a2a://agentsapplication/json所有 Agent 列表
a2a://agents/{name}application/json单个 Agent 详情

会话模式

MCP 服务支持两种会话模式：

  • 有状态模式：通过 SSE 建立长连接，响应通过 SSE channel 推送。适合 MCP 客户端（Claude Desktop、Cursor）
  • 无状态模式：直接 POST /mcp/messages 不带 session_id，响应作为 HTTP 响应体返回。适合脚本测试和 curl 调用
用途
MCP 集成让 Agent 无需自研 HTTP 客户端对接平台 API。直接通过 MCP SDK（如 Python/TypeScript MCP SDK）即可发现和调用其他 Agent，大幅降低 Agent 接入成本。

待决策问题

  1. 内建 Agent 是否属于平台核心能力？
    • 如果是：平台需要管理 LLM API Key、Provider 配置、模型选择、并发限制、Token 配额
    • 如果不是：内建 Agent 作为独立 Bridge Agent 存在，平台只做转发，降低耦合
  2. 安全边界：内建 Agent 调用 send_to_agent 时是否需要权限控制？read_file、write_file 是否需要沙箱？当前实现无限制。
  3. 资源隔离：多个内建 Agent 实例并发时的限制——当前子代理上限 3 个并发，超时 5 分钟。

行业参考
CrewAI

预定义角色和目标的 AgentTeam 模型。支持顺序编排（Sequential，A→B→C）、层级编排（Hierarchical，Manager 分配任务）、共识编排（Consensual，投票决策）。每个 Agent 有 role、goal、backstory 属性。

AutoGen (Microsoft)

Multi-Agent 对话框架。Agent 间可自由对话，支持两人对话（Two-Agent Chat）和群组对话（Group Chat）。Group Chat 有一个 Manager 角色，决定下一个发言的 Agent。支持人类参与（Human-in-the-loop）。

LangGraph

基于有向状态图的工作流编排。节点是函数或 Agent，边是条件转移。支持循环（用于迭代优化）、分支、并行。核心概念是 State（全局共享状态），Agent 通过读写 State 协作。

Google A2A 规范

不包含 AgentTeam 的概念。A2A 规范只定义了 Agent 间的点对点消息传递。AgentTeam 需要在 A2A 之上自行实现编排逻辑，或者由平台提供编排能力。

待调研问题
  1. AgentTeam 是否需要在平台层面提供编排能力，还是仅作为 Agent 侧的协作模式？
  2. 团队中 Agent 的负载均衡和故障转移如何处理？（如：某个 Agent 下线，任务自动分配给同类 Agent）
  3. 团队的生命周期管理：创建、动态加入/退出、销毁
  4. 共享上下文的实现方式：共享数据库？共享文件？通过消息传递？

3.3 Agent 交互编排（Workflow）

概念

定义 Agent 之间的协作流程，包括执行顺序、条件分支、循环等。编排解决的核心问题是：谁先做、谁后做、什么时候并行、什么时候停下来。

Workflow 类型

类型说明数据流适用场景
顺序（Sequential）A → B → C，按顺序执行每步的输出是下一步的输入流水线处理：翻译 → 校对 → 排版
并行（Parallel）A、B、C 同时执行结果汇总合并独立子任务：同时搜索 3 个数据源
条件分支（Conditional）根据 A 的输出决定走 B 还是 C分支选择，类似于 if-else分类：如果是代码问题 → Coder，否则 → General
循环（Loop）重复执行某步骤直到满足条件每轮输出反馈到下一轮迭代优化：生成 → 审核 → 修改，直到通过
人工审批（HITL）某个步骤需要人工确认暂停等待人工输入需要人类判断的决策点

编排方式深度对比

方式说明优点缺点适用阶段
代码编排在 Agent 或 Bridge 代码中硬编码流程完全灵活，可处理任意复杂逻辑不可复用，维护成本高，非技术人员无法修改第一版（Agent 自行编排）
配置编排YAML/JSON 声明工作流定义可复用、可版本控制、非技术人员可编辑灵活性受限，复杂逻辑难以表达第二版（平台提供 YAML schema）
图编排DAG 定义节点（Agent）和边（条件转移）直观展示复杂拓扑，支持并行和循环实现复杂度高，需要可视化编辑器第三版（LangGraph 风格）
事件驱动Agent 发布/订阅事件，按事件触发松耦合，可扩展，Agent 无需知道完整流程调试困难，流程不直观，死循环风险长期（微服务风格）

配置编排示例（YAML 设想）

workflow:
  name: research-pipeline
  steps:
    - id: search
      agent: researcher
      input: "{{user_message}}"
      output: search_result

    - id: analyze
      agent: analyst
      input: "{{search_result}}"
      output: analysis

    - id: draft
      agent: writer
      input: "{{analysis}}"
      output: draft

    - id: review
      agent: reviewer
      input: "{{draft}}"
      output: review_result
      # 条件分支：如果不通过则回到 draft 步骤
      on_condition:
        field: review_result.approved
        if_false: draft  # 回到 draft 步骤
        max_loop: 3      # 最多循环 3 次

行业参考详细分析

LangGraph — 基于状态图的编排

LangGraph 的核心思想是将工作流建模为有向图：

  • 节点（Node）：一个 Python 函数，接收当前 State，返回更新后的 State
  • 边（Edge）：条件转移函数，根据当前 State 决定下一个节点
  • State：全局共享状态，所有节点读写同一个 State 对象
  • Checkpointer：支持在任意节点暂停和恢复（用于 HITL）

与 A2A 平台的结合点：每个 LangGraph 节点可以是一个 A2A Agent，State 通过平台的消息传递来同步。但 LangGraph 是 Python 生态，与 Go 平台需要通过 MCP 或 REST API 桥接。

Dify — 可视化工作流编排

Dify 提供拖拽式可视化编辑器：

  • 内置节点类型：LLM、知识检索、代码执行、条件判断、变量赋值、HTTP 请求
  • 支持 DSL 导入导出（YAML 格式）
  • 调试模式：逐步执行，查看每个节点的输入输出
  • 与 A2A 平台的结合点：可将 A2A Agent 封装为 Dify 的自定义节点类型，通过 HTTP 请求节点调用 POST /agent/{name}

待调研问题

  1. 第一版是否需要在平台层面支持工作流，还是先让 Agent 自行编排？
  2. 如果支持，首选哪种编排方式？配置编排（YAML）的投入产出比最高
  3. 工作流的错误处理和重试策略：单个 Agent 失败时，是重试还是跳过还是整体终止？
  4. 工作流的版本管理：如何处理正在运行的工作流被更新？

3.4 MCP 集成

已实现的调研 已有原型

MCP 服务端

internal/handler/mcp_sse.go

  • SSE 传输，协议版本 2024-11-05
  • 暴露 3 个工具、1 个资源
  • 有状态（SSE channel）+ 无状态（直接 HTTP）双模式
  • 30s keepalive 心跳包
  • Session 管理：UUID session_id，内存 map 存储
MCP 客户端

internal/mcpclient/client.go

  • stdio 传输：启动子进程，通过 stdin/stdout 通信
  • SSE 传输：连接远程 MCP Server 的 SSE 端点
  • 自动发现工具：连接后调用 tools/list 获取可用工具列表
  • 工具调用：通过 tools/call 发送参数并获取结果
  • 内建 Agent 可接入任意 MCP Server 扩展工具能力

MCP 服务端协议流程详解

  1. 客户端连接：GET /mcp/sse → 平台创建 SSE Session，返回 endpoint 事件
  2. 客户端初始化：POST /mcp/messages?session_id=xxx，body: {"method":"initialize","params":{...}}
  3. 平台返回能力：{"protocolVersion":"2024-11-05","capabilities":{"tools":{},"resources":{}},"serverInfo":{"name":"a2a-platform"}}
  4. 工具发现：客户端调用 tools/list → 平台返回 3 个工具定义
  5. 工具调用：客户端调用 tools/call，指定工具名和参数 → 平台执行并返回结果
  6. 资源访问：客户端调用 resources/read，指定 URI → 平台返回资源内容

意义与价值

  • 降低接入门槛：Agent 无需实现 A2A HTTP 客户端，通过 MCP SDK（Python/TypeScript）即可接入
  • 兼容生态：Claude Desktop、Cursor 等 MCP 兼容客户端可直接使用平台能力
  • 工具层解耦：MCP 作为工具暴露的标准协议，解耦了"谁提供工具"和"谁使用工具"
  • 内建 Agent 扩展：内建 Agent 通过 MCP 客户端连接外部 MCP Server，无缝扩展工具能力

4.6 与现有原型的关系

当前仓库（a2a-platform-go）是一个功能完整的调研原型，包含了内建 Agent、Bridge、聊天界面等第一版不需要的能力。新建生产平台时需要：

复用
  • MCP 服务端/客户端实现（完整可用）
  • A2A 协议解析（JSON-RPC 解析、SSE 事件提取）
  • SSE 事件广播器（events/broadcaster.go）
  • 数据模型定义（model/types.go）
  • 数据库 Store 双方言实现（SQLite/MySQL 兼容）
  • 配置解析（环境变量展开）
重写
  • 注册/发现层：引入 etcd 替换内存 map + 定时轮询
  • 消息代理层：简化为纯转发，移除 builtin/bridge 分支
  • API 层：精简接口，只保留注册/发现/心跳/消息/事件
  • 中间件：重新组织认证、限流、日志
移除
  • 内建 Agent 引擎（engine/）
  • Bridge Agent 引擎（bridge/）
  • LLM Provider 抽象（llm/）
  • 聊天前端（web/admin/）
  • 会话管理（ContextStore、SubagentStore）
  • 追踪系统（TraceStore、追踪 API）

5开放问题 待讨论

  • 1
    etcd vs 自建心跳：第一版是否引入 etcd？还是先用简单的内存注册表 + 数据库持久化？判断依据：预期 Agent 规模和是否需要多实例部署。
  • 2
    消息持久化粒度：平台是否需要记录每条消息的完整内容？还是只记录转发元数据（来源、目标、时间、状态）？影响：存储成本和隐私合规。
  • 3
    Bridge 规范：是否需要为 Bridge 提供标准化的接入规范？如最少需要实现哪些 API（AgentCard 端点、消息接收端点、健康检查端点）。
  • 4
    内建 Agent 定位：内建 Agent 是平台核心能力还是可选组件？如果是核心，平台需要管理 LLM 配置和资源；如果是可选，解耦为独立服务。
  • 5
    工作流优先级：Agent 交互编排是否需要在平台层面支持？如果支持，与 Agent 侧自编排的边界在哪？建议：第一版 Agent 自编排，第二版平台提供 YAML 配置编排。
  • 6
    AgentTeam 平台角色：AgentTeam 编排是否属于平台能力？还是由 Agent 侧的编排框架（如 CrewAI）负责？平台只提供 Agent 间的通信通道。
  • 7
    多实例部署：如果平台需要水平扩展，SSE 连接如何在不同实例间同步？是否需要引入 Redis Pub/Sub 作为消息总线？
