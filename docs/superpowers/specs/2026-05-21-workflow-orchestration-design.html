1 Overview & 核心决策

在 A2A 平台中新增可视化 Workflow 编排模块。用户通过 YAML 定义多 Agent 协作的 DAG 流程，在 React Flow 画布上可视化编辑，由内置 Go 引擎按图执行。

核心决策一览

决策项选择理由
架构内置 Go 引擎（单体）与当前单二进制部署一致
编辑器交互自动布局 (dagre) + 可拖拽微调默认整洁，用户可调
存储数据库 + YAML 导入导出与现有 Agent 存储一致；文件可版本控制
节点间数据流共享状态（全局 KV）灵活，支持分支和并行
Agent 上下文每个 Agent 节点独立 contextId不污染 system prompt，仅传递结构化数据
节点类型
Agent Tool Conditional Parallel Loop Human
触发方式
Chat API Schedule Event
技术选型
React Flow + dagre + Monaco

2 YAML Schema

Workflow 定义完全基于 YAML，支持双向同步到可视化画布。

完整示例

workflows:
  customer-support:
    description: "Customer support workflow"

    input_schema:
      type: object
      properties:
        user_message: { type: string }
        priority: { type: string, enum: [low, medium, high] }

    shared_state:                          # 初始共享状态
      classification: null
      response: null
      approved: false

    nodes:
      classify:
        type: agent
        agent_name: classifier
        instruction: "Classify the user message"
        inputs: ["{{.input.user_message}}"]
        outputs:
          classification: "{{.result}}"
        timeout: 30s
        retry: { max: 2, backoff: exponential }

      route:
        type: conditional
        expression: "{{.state.classification}}"
        routes:
          BUG: handle_bug
          SUPPORT: handle_support
          default: general_response

      handle_bug:
        type: agent
        agent_name: bug-agent
        instruction: "Handle bug: {{.state.classification}}"
        inputs: ["{{.state.classification}}"]
        outputs:
          response: "{{.result}}"

      handle_support:
        type: parallel
        nodes: [lookup_order, check_faq]
        timeout: 60s

      lookup_order:
        type: tool
        tool_name: http_request
        config:
          url: "https://api.example.com/orders/{{.input.order_id}}"
          method: GET
        outputs:
          order_info: "{{.result.body}}"

      check_faq:
        type: agent
        agent_name: faq-agent
        outputs:
          faq_answer: "{{.result}}"

      human_review:
        type: human
        prompt: "Review: {{.state.response}}"
        timeout: 30m
        outputs:
          approved: "{{.result.approved}}"

      send_response:
        type: agent
        agent_name: responder

      general_response:
        type: agent
        agent_name: general-agent
        outputs:
          response: "{{.result}}"

    edges:
      - [START, classify]
      - [classify, route]
      - [route, handle_bug, { condition: BUG }]
      - [route, handle_support, { condition: SUPPORT }]
      - [route, general_response, { condition: default }]
      - [handle_bug, human_review]
      - [handle_support, send_response]
      - [human_review, send_response, { condition: approved }]
      - [send_response, END]
      - [general_response, END]

    triggers:
      - type: api
      - type: chat
        agent_name: support-wf
      - type: schedule
        cron: "0 9 * * 1-5"
        input: { report_type: "daily_summary" }
      - type: event
        event_type: "task.completed"
        filter: "agent_name == 'bug-agent'"

节点类型定义

类型必填字段说明
agentagent_name, instruction调用内置 Agent，通过 Engine.HandleRequest()
tooltool_name, config执行确定性工具（HTTP、函数等），不经过 LLM
conditionalexpression, routes计算表达式，路由到匹配分支
parallelnodes并发执行子节点，等待全部完成
loopnodes, condition, max_iterations循环执行子节点直到条件满足
humanprompt, timeout暂停执行，等待人工审批/输入

模板表达式

所有 inputs、instruction、prompt 字段支持 Go template 语法：

表达式含义
{{.input.xxx}}Workflow 运行输入参数
{{.state.xxx}}共享状态中的某个字段
{{.result}}当前节点的原始执行结果
{{.state}}整个共享状态对象（需 pass_full_state: true）

4 执行引擎

架构图

┌─────────────────────────────────┐ │ Workflow Engine │ │ internal/workflow/engine.go │ └──────────┬──────────────────────┘ │ ┌────────────────┼────────────────┐ ▼ ▼ ▼ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │ DAG Parser │ │ Executor │ │ State Store │ │ (YAML → DAG)│ │ (节点执行) │ │ (共享状态) │ └──────────────┘ └──────┬───────┘ └──────────────┘ │ ┌──────────────────┼──────────────────┐ ▼ ▼ ▼ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │Agent Executor│ │Tool Executor │ │Control Flow │ │(Engine. │ │(HTTP / 函数) │ │(条件/并行/ │ │ HandleRequest│ │ │ │ 循环) │ └──────────────┘ └──────────────┘ └──────────────┘

执行流程

解析 YAML → DAG
→
校验无环
→
创建 Run + 初始化 State
→
执行循环
→
END / Error
  1. 解析阶段：YAML → DAG 结构（节点 + 边），校验无环、有入度/出度
  2. 初始化阶段：创建 workflow_run，初始化共享状态，找到入度为 0 的起始节点
  3. 执行循环：
    • 从就绪队列取出节点（入度全部完成）
    • 根据节点类型分派执行器
    • 执行完毕后将输出写入共享状态，更新下游节点入度
    • 通过 Broadcaster 广播节点状态变更
    • 重复直到 END 节点或出错
  4. 并行执行：parallel 节点为子节点启动多个 goroutine，用 sync.WaitGroup 等待

各节点执行器

节点类型执行逻辑
agent调用 Engine.HandleRequest()，将渲染后的 instruction 和 inputs 传给指定 agent
tool执行内置工具函数或 HTTP 调用，直接返回结果，不经过 LLM
conditional计算 Go template 表达式，匹配 routes 中的分支，激活对应的下游节点
parallel为子节点列表启动并发 goroutine，等待全部完成（或超时）
loop循环执行子节点直到条件满足或达到最大迭代次数
human将状态改为 paused，通过 SSE 广播等待事件；前端展示审批界面，用户操作后恢复

错误处理

每个节点可配置：

retry:
  max: 2
  backoff: exponential    # fixed | exponential
  interval: 5s
timeout: 30s
on_error: fail            # fail | skip | fallback
fallback: error_handler_node_id
策略行为
fail标记整个 Workflow Run 为 failed
skip标记节点为 skipped，继续执行下游（空输出）
fallback路由到备选节点执行

5 共享状态模型

核心原则：Agent 之间不共享对话历史，只共享结构化数据。 每个 Agent 节点在独立的 contextId 中执行，仅通过 Workflow 引擎渲染的 instruction 和 inputs 接收数据。

数据流示意

用户输入 │ ▼ ┌──────────────────────────────────────────────────┐ │ Workflow 共享状态 │ │ │ │ input: { user_message: "...", priority: "high" }│ │ state: { │ │ classification: "BUG", ← Agent A 写入 │ │ order_info: { ... }, ← Tool 节点写入 │ │ response: "...", ← Agent B 写入 │ │ approved: true ← Human 节点写入 │ │ } │ └──────────────────────────────────────────────────┘ 执行流: classify Agent (独立 context) → 写入 { classification: "BUG" } → handle_bug Agent (独立 context，只收到 "BUG" 标签) → 写入 { response: "已创建工单 #123..." } → human_review (展示回复，用户审批) → 写入 { approved: true }

为什么这样设计

方案优点缺点
共享对话历史Agent 看到完整上下文system prompt 冲突、token 浪费、隐私泄露
共享结构化数据（当前方案）干净、可预测、token 高效Agent 看不到前序节点的完整推理

如需 Agent 感知更多上下文，可在 instruction 中传入更多字段，或设置 pass_full_state: true 将整个共享状态渲染到指令中。

双向同步机制

  • 画布 → YAML：拖拽/编辑后，将 React Flow 的 nodes/edges 序列化为 YAML
  • YAML → 画布：编辑 YAML 后，解析并重新生成 nodes/edges
  • 用 dagre 自动布局，允许用户微调后保存位置
  • Debounce (300ms) 防循环更新，syncedYamlRef 打破循环渲染

运行监控

Run Detail 页面在 Workflow 画布上叠加实时状态：

  • pending 灰色 — running 蓝色 spinner — completed 绿色 check — failed 红色 X
  • 点击节点查看 input/output/error 详情
  • Human 节点暂停时弹出审批对话框
  • 实时更新通过 SSE 事件推送

Chat 触发机制

Workflow 配置了 triggers: [{ type: chat, agent_name: "support-wf" }] 后，注册为虚拟 Agent。当 /agent/:name 收到请求时：

  1. Handler 检查 WorkflowStore（优先于 Builtin/Bridge/External）
  2. 提取用户消息作为 input
  3. 创建 Workflow Run
  4. 最终输出通过 SSE 流式返回 Chat 界面

定时触发

引擎启动时解析 schedule 触发器，注册到 cron 调度器（如 robfig/cron），按 cron 表达式自动创建 Run。

事件触发

引擎订阅 events.Broadcaster，匹配 event_type 和 filter 表达式，命中时自动创建 Run。
